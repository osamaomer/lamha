# CLAUDE.md: working on Lamha

Claude Code loads this file at the start of every session. It explains how the code is built, the rules it follows, how to find code and test it cheaply, and **what is still open**. It is read in every session, so keep it short: the history of past work lives in [docs/history.md](docs/history.md), undecided plans in [docs/ideas.md](docs/ideas.md).

## What Lamha is

An Arabic-first dictionary, translator and English writing coach (the user's own project; the user is Arabic-speaking and writes the product copy in Arabic and English). Two products share one codebase:

- **Firefox extension** (repo root): MV3, Firefox 140+, no build step, no runtime dependencies.
- **Windows app** (`desktop/`): Electron 44. It runs the extension's files **unchanged**.

User-facing documentation lives in [README.md](README.md). Update it whenever a feature changes.

## Architecture in one page

**One brain, two hosts.** `background.js` owns everything that matters: network calls (Google Translate, Wikipedia, speech), the three AI providers (Claude, Gemini, Ollama), settings, lookup history, the flashcard deck (SM-2) and the mistake journal. Pages never call the network. They send messages:

`lookup · translateBatch · wiki · speak · stopSpeak · ai · aiTest · ollamaModels · reviewQueue · reviewGrade · today · cardRemove · cardToggle · cardHas · cardsClear · dataExport · dataImport · deckSync · deckSyncNow · diagnostics · relayPage · dictMeta · getSettings · setWordDict · writeTipSeen · packList · packInstall · packRemove · wikiOpen · appStatus · appLink · openOptions` (the switch at the bottom of `background.js`). In the Windows app the card and the reader may send only what the card does (`OUTSIDE_TEXT_MESSAGES` in `desktop/app-rules.js`).

- **Firefox:** the manifest loads `local-dict.js`, `packs.js`, `shared/i18n.js`, `shared/lamha-ai.js` and `background.js` as the background. Content scripts (`shared/*`, `content/styles.js`, `content/page-translator.js`, `content/content.js`) run in every frame.
- **Desktop:** `desktop/main.js` builds a `browser.*` stand-in, then loads the same background files with `vm.runInThisContext`. `preload.js` gives pages (popup = main window, options = Settings) their `browser.*`. The floating card over other apps is `renderer/card.html` with **the same content scripts injected**, so `content/content.js` must keep working in both (see `window.lamhaDesktop` and `external` messages).
- **Storage:** `storage.sync` holds settings (`DEFAULT_SETTINGS` in background.js, mirrored in `options.js` and `content.js`). `storage.local` holds per-device data: history, cards, mistakes, API keys, provider choice. On desktop both are JSON files in `%APPDATA%\Lamha` (`desktop/storage.js`).
  - **The deck** is kept in memory by the background (`deckMem`); every write carries `cardsRev`, and a deck change without the number just written (another writer) drops the copy. Only the background writes the deck: Settings' "delete all" is the `cardsClear` message. Each card has `mod` (last change); `cardsRemoved` notes deletions (180 days) so a backup or the other copy doesn't bring a word back. `mergeCards()` joins decks (backups, the Firefox ↔ app sync): the schedule of the copy reviewed last, text fields filled from either.
- **Interface language:** strings are `[arabic, english]` pairs. Shared ones are in `shared/i18n.js`, settings-page ones in `options/i18n-options.js`, desktop ones in `desktop/renderer/i18n-desktop.js`. Use `LamhaI18n.t(key, vars)`. Never hard-code visible text in one language.
- **Offline dictionary:** `local-dict.js` reads sharded JSON from `dict/` (generated by `tools/build_dict.py`, don't hand-edit): `en/<xx>.json` and `forms/<xx>.json` by a word's first two letters, `ar/<code>.json`.
- **Offline Wikipedia** (Windows app only): `desktop/zim.js` reads Kiwix's `.zim` files, `desktop/wiki-library.js` keeps the list, downloads, summaries and the reader's articles, and main.js gives the background `LamhaWikiOffline` (`langs()`, `summary(titles, lang)`); `wikiSummary()` in background.js uses it when it exists. Settings' section is `desktop/renderer/wiki-settings.js` (bridge `lamhaWiki`, IPC `lamha:wiki`). The reader is `desktop/renderer/wiki/` (pictures through the `lamha-wiki:` protocol; articles are only ever shown through `sanitize.js`).
- **Language packs** (French–French, German–German, Spanish–Spanish, Turkish–Turkish): `packs.js` downloads them from a GitHub release and keeps them per device (IndexedDB in Firefox; files through `desktop/pack-store.js`, given to the background as `LamhaPackStore`). Built by `tools/build_packs.py` into `dist-packs/` (git-ignored).
- **Translation service:** every translation goes through `translateBatch()` / `lookup()` → `trSettings()` + `trPlan()`, which pick Google (`googleBatch`, `onlineLookup`) and/or the AI (`aiBatch`, `aiLookup`) in order, and `tryEngines()`, which runs them with fallback.
  - Settings live in storage.local: `trService`, `trProvider`, `trModels`, `trPages`.
  - AI calls, for writing and translation alike, go through `aiProviderConfig()` + `aiComplete()`.
  - Every AI translation passes `strayLetters()` (the foreign-script guard). Pages learn about the translator through `LamhaAI.translator()`.

## Rules the code follows

- **Match the surrounding style:** double quotes, semicolons, small helpers such as `h()` for DOM building, short "why" comments in plain English. There's no framework and no bundler.
- **Security and privacy:**
  - API keys never reach content scripts or the desktop card. Pages read `aiKeySet` / `geminiKeySet` flags (`LamhaAI.PROVIDER_KEYS`), and `main.js` strips `SECRET_KEYS` for the card.
  - Clipboard contents and user text are never logged. Log lengths or error *names* only.
  - Untrusted keys (model output, words used as object keys) are checked with `Object.hasOwn`, or stored in prototype-less objects.
  - Pages never use `innerHTML` with dynamic text. Build nodes with `h()` / `textContent`.
- **Animations** go through `LamhaMotion` (`shared/motion.js`). They only move transform and opacity, never block a result, and create nothing at level "off". While waiting for an answer, the Lamha mark shows `LamhaMotion.wait(host, kind)`: "book" (a word), "lens" (a sentence), "write" (the AI), after 250 ms; its motion is in `content/styles.js` (the card) and `motion.css` (the pages), mirrored for English.
- **Stale async work** is cancelled with request tokens (`reqId`, `qToken`, `wrToken`). Keep that pattern when adding async UI.
- **New root files** that aren't part of the extension must be added to `ignoreFiles` in `web-ext-config.mjs`. Extension folders the desktop app needs must be in `ITEMS` in `desktop/scripts/sync-ext.mjs`.
- **Versions** live in three places and move together: `manifest.json`, `desktop/package.json` and `desktop/package-lock.json` (via `npm version … --prefix desktop`).
- **Every release has an entry in `shared/changelog.js`** (Arabic and English): the Windows app's Settings → Updates shows it, and the release workflow turns it into the GitHub release notes (`tools/release-notes.mjs`); the release stops without one, and test-desktop checks the manifest's version has one.
- **Commit messages** look like `Lamha 1.8.0: animations you can switch` for releases; smaller commits describe the change plainly.
- **Line endings are mixed:** `background.js`, `content/content.js`, `local-dict.js`, `popup/popup.html` and `options/options.html` (among others) are stored with CRLF, most files with LF. Git Bash's `sed -i` strips the CRs and the whole file then shows as changed: edit with the editor, or write bytes as they were. Check with `git diff --stat` before committing.
- **The Windows app's pages** have a CSP (popup, options, card, panel, reader); Electron grants pages nothing but clipboard writing (`lockPermissions`); `content.js` ignores untrusted (page-scripted) mouse and key events; the build checks its own `app.asar` (fuses `onlyLoadAppFromAsar`, `enableEmbeddedAsarIntegrityValidation`). Decisions that need no Electron go in `desktop/app-rules.js`, tested in test-desktop.
- **Colours change in three places:** `shared/ui.css` (its two dark blocks must stay identical) and the card's `.root` / `.root.dark` in `content/styles.js`; a test in test-ui compares them. Corners use `--r-sm` / `--r-md` / `--r-lg`.
- **No system-styled controls:** dropdowns are styled once, in `shared/ui.css` (the Windows app draws the open list with `appearance: base-select`; Firefox draws its own, in our colours); questions use `LamhaDialog` (`shared/dialog.js`), never `confirm()` / `alert()` / `prompt()`; checkboxes are `.switch`, radio buttons `.choice` cards. A test in test-ui checks the first two.
- **Icons:** line icons in structural places (buttons, section titles, choice cards); emoji only in celebrations (🎉 🔥 👋), warnings (⚠️) and prose.

## Working with the user

- They care a lot about **alignment and spacing**: check edges and gaps in every new or changed screen (`npm run shots` for pictures).
- Settings' long intro paragraphs and other product copy are **their own words**: ask before rewriting them.
- They often report bugs with screenshots or GIFs; reproduce from the picture before guessing.

## Finding code (read less, jump straight there)

1. Use the map below to pick the file, then `Grep` for the function or message name.
2. Big files have section headers. `grep -n '^ */\* --' <file>` prints a file's table of contents with line numbers (background.js, content.js, main.js, popup.js, options.js).
3. Read only the part you need (`offset` / `limit`, about 80 lines around the hit). **Never read background.js (~2,100 lines), content.js, main.js or a test file whole.** Read a whole file only when it's short (under ~300 lines) or the task rewrites most of it.
4. When the user doesn't know where something lives, search by what the user sees: the Arabic or English string (`shared/i18n.js`, `options/i18n-options.js`, `desktop/renderer/i18n-desktop.js`) gives its key, and the key leads to the code.

## Testing only what changed

Each test file takes a name filter and `-q` (quiet: only failures and the total; `tools/test-args.mjs`):
`node tools/test-writing.mjs -q deck` runs the tests whose name contains "deck".

| Changed | Run | Time |
|---|---|---|
| `background.js`, `local-dict.js`, `packs.js` | `test-writing` (+ `test-ui` if pages use what changed) | ~19 s |
| `content/*`, `popup/*`, `options/*`, `shared/*`, `desktop/renderer/wiki/*` | `test-ui` (always runs whole: its steps build on each other) | ~30 s |
| `desktop/clipboard-*.js`, clip tools | `test-clipboard` | <1 s |
| `desktop/updater.js` | `test-updater` | <1 s |
| other `desktop/*.js` (not main.js), `shared/changelog.js`, the version | `test-desktop` | ~4 s |
| `desktop/main.js`, `preload.js` | no unit tests: `npm run smoke` (ask the user first: it takes over the mouse, keyboard and clipboard) | |

- While working, run the matching file with `-q` and a filter. **Before every commit run the whole suite once** (`npm run test:quiet`) and the lint.
- Test helpers: test-writing's `makeEnv({ realDict, events, scale, local, sync })` (background.js in a VM with a fake network) and `atTime(env, tz, iso, fn)`; test-ui's `openPage()`, `cardPage()`, `readerPage()` (dispatched events count as the user's unless marked `byPage`).
- Read only the tail of long command output (`| tail -30`), and look at only the screenshots that matter (each picture costs about 1,500 tokens).

## Sessions and models

- **One task per session.** When the user starts something unrelated to what this session did, suggest `/clear` in one line before starting.
- **Model:** at the start of a task, judge its size and say so in one line only when the session's model doesn't fit. Claude can't switch models itself; the user types `/model`.
  - Routine (Sonnet is enough): strings and translations, CSS and alignment, a fix in one function with a known cause, docs, the changelog, a version bump, running tests.
  - Complex (Opus): anything crossing hosts (Firefox ↔ app, background ↔ pages), security or privacy, the deck and its sync, async races, a bug with an unknown cause, audits, design work, new features.

## Compact instructions

When compacting, keep: the task and the user's decisions, files changed and why, test results (pass counts and any failure text), and what's left to do. Drop file contents that were only read, and passing test lists.

## Commands

```bash
npm install && npm test           # root: all five test files (tools/test-*.mjs); jsdom is needed for test-ui
npm run test:quiet                # the same, printing only failures and totals (use this before commits)
node tools/test-writing.mjs -q <words>   # one file, only tests whose name contains <words> (not test-ui)
npm run lint                      # web-ext lint, expected 0 errors / 0 warnings (CI uses --warnings-as-errors)
npm run bench                     # performance numbers (tools/bench.mjs): lookups on a simulated network (150 ms, dead, down),
                                  # the dictionary, the deck, desktop storage / clipboard / .zim (LAMHA_BENCH_ZIM), content scripts
cd desktop && npm install && npm start   # run the Windows app from source
cd desktop && npm run smoke       # full desktop self-test (needs a real Windows desktop; run before a release)
cd desktop && npm run shots       # every screen as a PNG, light/dark × ar/en (~5 min; LAMHA_SHOTS_ONLY=dark-ar for one set, LAMHA_SHOTS=folder).
                                  # Uses Ollama when it runs on this PC (real proofread / improve / AI translation); LAMHA_SHOTS_AI=0 skips it
```

- Desktop dependencies on a PC with npm 11: `npm ci` skips install scripts, so afterwards run `node node_modules/electron/install.js` and, in `node_modules/koffi`, `node ./cnoke.cjs -P . -D src/koffi --prebuild --release`. CI uses Node 22 (npm 10), which doesn't need this.

CI (`.github/workflows/checks.yml`) runs `npm test` and the lint on every push. Tagging `vX.Y.Z` runs the release workflow; `packs-v*` builds and publishes the language packs (packs-v1 is out).
